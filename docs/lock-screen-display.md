# Experimental lock-screen keyboard display

Settings → Experimental → **Show keyboard on lock screen** enables an experimental display path for the existing Tastko keyboard. It defaults off. Turning it off detaches the keyboard from the private display space. The keyboard remains nonactivating and keeps its existing geometry policy.

Enabling the option checks attachment and restoration while unlocked. On a screen-lock notification, Tastko shows the expanded keyboard, attaches it to its own private display space, and pauses pointer auto-hide and text predictions. The expanded keyboard stays visible: Close, Minimize, menu hide, hot-corner toggles, and native window hide/miniaturize/close actions cannot dismiss it while locked. The keyboard remains interactive, including normal keys, modifiers, Delete, language selection, and function-toolbar row toggling. Unlock restores the previous expanded/minimized and visible/hidden state, then restarts pointer monitoring with the user's existing preferences.

## Explicit key delivery and privacy

Physical keys use paired `CGEvent` key-down/up events at `.cghidEventTap`. Clicked text keys use paired Unicode events at the same system-focus route while locked. This path does not resolve an Accessibility target, read a field, activate a previous user application, or select a PID. Event-post permission is checked before locked key delivery. A submitted event does not establish that macOS accepted it; the operating system can reject events at protected input surfaces.

Predictions and context are cleared when locking, and pending prediction delivery to an old validated target is rejected. Diagnostic field reads pause while locked. Lock-mode receipts contain no key identity, text, target, or character count and are not retained in the debug state. Held repeats and queued clicks are invalidated across lock/unlock transitions. The normal `AccessibilityService.focusedKeyboardTarget()` secure-field exclusion is unchanged; it is not used by explicit lock-mode event posting. No code captures or assembles a password, submits authentication automatically, or changes authentication policy.

## Private interface boundary

`PrivateDisplaySpace` adapts the MIT-licensed [SkyLightWindow implementation](https://github.com/Lakr233/SkyLightWindow/blob/a28588bc5222b8daf6c4b46afb462a5d31495685/Sources/SkyLightWindow/SkyLightOperator.swift). The included `SkyLightWindow-LICENSE.txt` retains its notice. The bridge dynamically resolves SkyLight functions, creates one space at upstream's level 400, and configures only Tastko's own window. Missing symbols and rejected space-level configuration report an unavailable status. It snapshots the window's original spaces, falling back to the active desktop for a panel without explicit membership; detaching restores those spaces and removes/destroys only the space it created. Legacy space-ID widths and void lifecycle signatures are cross-checked against [CGSInternal's declarations](https://github.com/NUIKit/CGSInternal/blob/master/CGSSpace.h). The upstream visibility/attachment return declarations produced pointer-like values on this build; those calls are treated as void. Ordinary window-space queries also omit the special space. Successful setup therefore means the configured operations completed, not that lock-screen visibility was verified.

[Boring Notch's source](https://github.com/TheBoredTeam/boring.notch/blob/99900bf630a3d3e97fae079df2175993318d51f7/boringNotch/components/Notch/BoringNotchSkyLightWindow.swift) uses the same SkyLightWindow dependency. Its app is GPLv3; none of its implementation is incorporated here.

The private symbol signatures, level values, and distributed lock/unlock notification names are undocumented Apple interfaces. Symbol presence and successful return codes do not guarantee future ABI compatibility or visibility during authentication. This feature is not a guarantee of App Store acceptance. No privileged agent, injected code, authentication-policy changes, or new security entitlements are installed. This is an existing-session lock-screen experiment, not FileVault preboot or initial login support. Launch Tastko while unlocked before testing; launching it into an already locked session is unverified.

## Manual verification

Build and launch Tastko, enable the experimental setting, then lock the Mac manually. Check that the keyboard stays visible and interactive. Unlock normally and confirm its previous geometry, visibility, pointer behavior, and predictions are restored. No automatic lock/logout is performed. Do not enter or inspect credentials as part of display verification.
